# HU-S1-03 — Creación de cuentas institucionales

## Alcance

Implementación de la historia aprobada en `docs/sprint-1.md`: creación administrativa de cuentas institucionales, configuración de la contraseña por su titular e identificación de usuario, rol e institución al autenticarse. Reutiliza Sanctum con sesiones y cookies de HU-S1-01 y las instituciones de HU-S1-02.

Incluye el reenvío del enlace exclusivamente mientras la cuenta siga pendiente de su primera contraseña. No incluye alumnos, cuentas de empresa o Secretaría, ni recuperación o restablecimiento de contraseñas ya establecidas de HU-S1-04.

## Modelo y validaciones

| Elemento | Regla |
| --- | --- |
| `users.institution_id` | Clave foránea a `institutions.id`, sin eliminación en cascada. Nullable para cuentas existentes de otros roles; obligatoria en esta alta. Debe ser un entero positivo y apuntar a una institución activa. |
| `name` | Obligatorio, cadena de hasta 120 caracteres. |
| `email` | Obligatorio, formato email, hasta 254 caracteres; se normaliza a minúsculas sin espacios exteriores. Único en todos los usuarios mediante validación y restricción de base de datos. |
| `role` | El servidor asigna `INSTITUTION`, aunque el cliente envíe otro valor. |
| `is_active` | El servidor asigna `true` a la cuenta nueva. |
| `password_setup_required` | `true` para cuentas creadas mediante esta funcionalidad. La migración usa `false` como valor inicial para conservar las credenciales de cuentas existentes. No se acepta desde el cliente ni se serializa. |
| `password` | Hash con bcrypt mediante `Hash::make` al configurar la contraseña y el cast `hashed` del modelo. Está en `$hidden` de `User`. Nunca se devuelve en el alta, login ni `/api/me`. |

El alta administrativa no valida ni acepta una contraseña: un campo `password` añadido manualmente se ignora. Se genera una credencial aleatoria inaccesible al administrador para satisfacer la columna no nullable; la cuenta permanece bloqueada hasta completar su configuración.

La migración `2026_09_30_000002_add_initial_password_setup.php` agrega la bandera y la tabla `institution_password_setup_tokens`. Esta tabla almacena el **hash del token**, asociado al correo y a su fecha de creación; no almacena el enlace en texto plano.

## Contraseña inicial

1. ADMIN crea la cuenta indicando nombre, correo e institución.
2. El backend usa `Password::broker('institution_setup')` para generar un token aleatorio. El enlace caduca en 60 minutos y solo puede consumirse una vez.
3. Después del commit, `SetInitialPassword` envía el enlace al correo registrado de la persona titular. En `local` se usa SMTP hacia Mailpit; en producción debe configurarse un transporte real y `FRONTEND_URL` con el origen HTTPS confiable de React. `testing` omite el correo para mantener las pruebas aisladas.
4. Exclusivamente en `testing`, el `201` contiene `setup_url` para E2E. En `local` y producción la API nunca devuelve el enlace, tampoco al reenviarlo. React lo descarta incluso en pruebas. `Cache-Control: no-store, private` evita almacenamiento en caché, pero no sustituye esa exclusión del JSON.
5. El titular visita `/set-initial-password?email=...&token=...` y establece su contraseña con confirmación. Debe tener al menos 12 caracteres y como máximo **72 bytes**, límite de bcrypt. Los caracteres multibyte alcanzan ese máximo antes; se rechazan bytes nulos. Incluso una contraseña que tenga formato de hash bcrypt se procesa como texto literal y recibe un nuevo hash.
6. La API comprueba token, caducidad, rol, vinculación, estado y configuración pendiente. Cambia el hash, elimina el token y desmarca la bandera dentro de una transacción con bloqueo del usuario. Un enlace consumido no puede reutilizarse, incluso con peticiones concurrentes.
7. Al cargar la página, React captura correo y token únicamente en memoria y reemplaza la URL inmediatamente, antes del envío del formulario. El documento aplica `Referrer-Policy: no-referrer`, también mediante una etiqueta meta anterior a los recursos. Tras el éxito se borran las credenciales de memoria. Al recargar antes de completar el formulario es necesario volver a abrir el enlace del correo. El usuario inicia sesión de forma explícita; configurar la contraseña no inicia una sesión ni sustituye la sesión de otro usuario.

La ruta pública de configuración requiere CSRF y tiene límites de 5 solicitudes por correo y 10 por IP por minuto. No necesita una sesión autenticada. No permite restablecer contraseñas de cuentas ya configuradas, otros roles o cuentas sin institución. El reenvío administrativo que se describe a continuación solo sirve para finalizar altas pendientes; no habilita recuperación de contraseñas existentes.

## Envío después del commit y recuperación del alta pendiente

La transacción almacena la cuenta y el hash del token. `InitialPasswordLink::deliverAfterCommit` registra el envío mediante `DB::afterCommit`; el correo se intenta únicamente después de confirmar los datos. Si falla o se revierte la transacción, no se envía una notificación. La unicidad de correo en PostgreSQL protege también registros concurrentes y se traduce a un error de validación.

El envío sigue siendo síncrono, con timeout SMTP de 10 segundos. Un fallo del transporte se captura sin revertir la cuenta ya confirmada ni simular un fallo de creación. La respuesta `201` conserva los datos del usuario y añade `setup_delivery`:

| Valor | Significado |
| --- | --- |
| `sent` | El transporte aceptó el mensaje; no confirma recepción en el buzón. |
| `pending` | El envío no quedó confirmado. La cuenta sigue creada, pendiente y recuperable mediante reenvío. |
| `testing` | No se contactó un transporte; el enlace está disponible solo para pruebas automatizadas. |

Un proceso también puede interrumpirse después del commit y antes de enviar o responder. Por eso ADMIN dispone de **Reenviar enlace de configuración**, accesible en el detalle de la institución incluso después de recargar la página. Introduce el correo de la cuenta pendiente; el backend busca el usuario dentro de esa institución y envía al correo ya registrado, sin aceptar otro destinatario ni revelar el enlace.

El reenvío requiere `ADMIN`, CSRF, usuario `INSTITUTION` activo, institución activa y `password_setup_required = true`. Bloquea el usuario antes de verificar estas condiciones y de rotar el token. No cambia la contraseña, identidad, rol ni institución. Rechaza cuentas inexistentes, de otra institución o con contraseña ya establecida. El token previo queda inválido; el titular debe abrir el mensaje más reciente. Si el nuevo envío falla, puede reintentarse después de un minuto.

Hay un intervalo mínimo persistido de 60 segundos desde la última emisión (incluida el alta) y un límite adicional de 10 solicitudes por ADMIN por minuto. Los intentos limitados no rotan el token. No hay reintentos automáticos ni promesa de entrega exactamente una vez: un transporte puede aceptar el mensaje y perderse su confirmación. La recuperación es manual y permanece disponible mientras la cuenta esté pendiente; se registran solo el identificador de cuenta y el tipo de excepción, nunca el token, la URL ni mensajes del transporte que puedan contener secretos.

Laravel documenta [el envío después del commit para notificaciones en cola](https://laravel.com/framework/docs/13.x/notifications#queued-notifications-and-database-transactions). Aquí se conserva la infraestructura síncrona del MVP y se usa el callback de transacción con recuperación explícita. La retirada del token y la política de referencia siguen la [guía OWASP para enlaces de contraseña](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#url-tokens).

## Buzón local

`compose.yaml` incluye [Mailpit](https://mailpit.axllent.org/docs/install/docker/), con la interfaz disponible únicamente en `http://localhost:8025` (configurable mediante `MAILPIT_PORT`). SMTP usa `mailpit:1025` dentro de la red Docker, sin publicar ese puerto al host. El backend local usa este transporte en lugar de escribir enlaces en logs. Para iniciar el buzón: `docker compose up -d mailpit`; al recrear el backend se aplican las variables SMTP del Compose.

Las peticiones de configuración y de obtención de su cookie CSRF usan explícitamente `referrerPolicy: no-referrer`. Para identificar la SPA ante Sanctum, las demás peticiones al backend envían únicamente el origen mediante `referrerPolicy: origin`, sin ruta, correo ni token.

El buzón es una herramienta del entorno de desarrollo para representar al titular, no una funcionalidad ni un enlace de la interfaz ADMIN. En producción deben configurarse un transporte y buzones reales. La política `Referrer-Policy: no-referrer` está configurada en Vite para desarrollo/preview y en el HTML; el servidor que publique el frontend compilado debe conservar también esa cabecera.

## Instituciones inactivas

- No se crean cuentas para instituciones inexistentes o inactivas; se revalida el estado bajo bloqueo durante el alta.
- Si la institución se inactiva, ninguna cuenta vinculada puede iniciar sesión ni acceder a endpoints autenticados, aunque la cuenta conserve `is_active = true`.
- El login rechaza credenciales correctas de una institución inactiva con `401` y código `INSTITUTION_INACTIVE`. Las credenciales incorrectas mantienen el error genérico de validación.
- El middleware vuelve a consultar el estado en cada petición autenticada. Ante una institución inactiva devuelve `401`, cierra la sesión e invalida su cookie y token CSRF.
- La configuración inicial de una cuenta o institución inactiva devuelve `403` (`ACCOUNT_INACTIVE` o `INSTITUTION_INACTIVE`), sin consumir el enlace válido.
- Inactivar conserva usuarios, relaciones, contraseñas e información histórica. Reactivar permite nuevos inicios de sesión; una sesión ya invalidada requiere autenticarse otra vez.

## Contrato API

| Método y ruta | Cuerpo | Respuesta |
| --- | --- | --- |
| `POST /api/institution-accounts` | `name`, `email`, `institution_id` | `201`, `{data: {id, name, email, role, is_active, institution: {id, name}}}`. Añade `setup_delivery` y, únicamente en `testing`, `setup_url`. Requiere `auth:sanctum`, middleware `active` y rol `ADMIN`. |
| `POST /api/institution-accounts/resend-setup` | `email`, `institution_id` | `200`, `{setup_delivery}` y `setup_url` solo en `testing`. Requiere sesión activa y rol `ADMIN`; únicamente para cuentas pendientes de la primera contraseña. |
| `POST /api/institution-accounts/password-setup` | `email`, `token`, `password`, `password_confirmation` | `204` al completar la configuración. Acceso público con token válido, CSRF y limitación de solicitudes. |
| `POST /api/login` | `email`, `password` | Conserva el contrato de sesión y añade `user.institution: {id, name}` o `null`. |
| `GET /api/me` | — | Devuelve `user` con identidad, rol e institución vinculada o `null`. Requiere sesión y cuenta/institución activas. |

Errores relevantes:

- `401`: sesión ausente/inválida, institución inactiva o configuración pendiente (`PASSWORD_SETUP_REQUIRED`) cuando se acreditó la contraseña.
- `403`: rol no autorizado para crear cuentas o reenviar enlaces; cuenta o institución inactiva durante la configuración inicial.
- `419`: CSRF ausente o inválido.
- `422`: datos inválidos, correo duplicado, institución inválida, cuenta no elegible para reenvío o enlace inválido/caducado/usado. Los problemas del enlace se comunican en `errors.token`, sin revelar si existe el usuario.
- `429`: se excedió el límite de intentos o el intervalo mínimo de reenvío; incluye `Retry-After`.

## Interfaz

En `/institutions/:id`, ADMIN ve `InstitutionAccountForm` cuando la institución está activa. Solo solicita nombre de la cuenta y correo de acceso; el identificador de institución procede del detalle. Presenta validaciones, errores de red/API, estado de envío y confirmación de alta, y evita envíos duplicados. `InstitutionAccountSetupLinkForm` permite reenviar por correo mientras el alta siga pendiente; la interfaz distingue un alta creada con envío pendiente de un mensaje aceptado por el transporte.

La ruta pública `/set-initial-password` funciona independientemente de la restauración de sesión, también si el navegador tiene una sesión ADMIN. La sesión institucional muestra la institución vinculada y mantiene la denegación de navegación y API administrativas. React presenta mensajes definidos por códigos conocidos para la institución inactiva o la configuración pendiente.

## Cobertura de aceptación

| Criterios | Verificación |
| --- | --- |
| CA-01, CA-09, CA-10 | Pest verifica sesión obligatoria, ADMIN permitido y roles INSTITUTION/COMPANY/SECRETARY denegados, también con solicitudes directas. Vitest y Playwright verifican navegación y permisos. |
| CA-02, CA-03 | Validación y clave foránea; rechazo de instituciones inexistentes/inactivas y asociación del usuario con una única institución. |
| CA-04 | Asignación forzada de INSTITUTION y rechazo de escalamiento mediante campos manipulados. |
| CA-05 | Normalización, validación y restricción única global del correo; rollback ante colisiones concurrentes. |
| CA-06 | Hash con bcrypt; contraseña oculta en serialización; ADMIN no establece la contraseña; token almacenado como hash, con caducidad y uso único. |
| CA-07, CA-08, CA-12 | Configuración por el titular, login y `/api/me` con identidad, rol e institución; bloqueo de login y sesiones al inactivar la institución. |
| CA-11 | Sin funciones nuevas para COMPANY o SECRETARY; acceso administrativo denegado. |

Pest incluye fallo de transporte después del commit, ausencia de correo al revertir, aislamiento de `setup_url` por entorno, reenvío limitado a pendientes y validación de contraseña por bytes, confirmación, token inválido/caducado/reutilizado, CSRF, rate limiting y aislamiento respecto de recuperación de contraseñas. Vitest y React Testing Library cubren formulario administrativo, cliente HTTP, configuración inicial y presentación de sesión/errores.

El E2E crea institución y cuenta sin contraseña como ADMIN, extrae `setup_url` del `201`, abre un contexto independiente para el titular, configura su contraseña e inicia sesión. Comprueba URL limpia antes de introducir la contraseña, cabecera/meta `no-referrer` y ausencia de `Referer` en las solicitudes de configuración. También verifica el rol y la institución, denegación administrativa, rechazo del reenvío una vez establecida la contraseña y rechazo de acceso después de inactivar la institución.

## Verificación reproducible

Desde la raíz, ejecutar secuencialmente:

```sh
docker compose run --rm --no-deps frontend npm run test
sh scripts/test-e2e.sh
sh scripts/test-backend.sh
```

Los scripts usan un proyecto Docker y bases de datos de pruebas aislados de desarrollo. Las credenciales E2E son efímeras. Las migraciones se aplican automáticamente en ese entorno; para actualizar una instalación local existente, ejecutar `docker compose exec backend php artisan migrate`.
