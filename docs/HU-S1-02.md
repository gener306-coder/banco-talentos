## Diseño técnico

Decisiones documentadas antes de implementar las validaciones CA-04 y CA-05:

| Campo | PostgreSQL | Validación HTTP |
| --- | --- | --- |
| `id` | Clave primaria autoincremental | Generado por el servidor. |
| `name` | `varchar(255) NOT NULL` | Obligatorio, string, máximo 255 caracteres. |
| `cct` | `varchar(255) NOT NULL UNIQUE` | Obligatorio, string, máximo 255 caracteres, único. |
| `contact_email` | `varchar(254) NOT NULL` | Obligatorio, string, email, máximo 254 caracteres. |
| `is_active` | `boolean NOT NULL DEFAULT true` | Solo la acción de estado acepta un booleano JSON explícito. |
| `created_at`, `updated_at` | Timestamps de Laravel | Administrados por el servidor. |

La unicidad de `cct` se aplica también a instituciones inactivas. Al editar se
excluye únicamente el registro resuelto por el identificador de la ruta. No se
impone un formato oficial ni conversión a mayúsculas del CCT; se utiliza la
igualdad de PostgreSQL y el recorte de espacios habitual de Laravel. Nombre y
correo de contacto pueden repetirse. La base de datos garantiza unicidad y
ausencia de nulos; el FormRequest valida además cadenas no vacías y formato email.

El alta siempre produce una institución activa. Alta y edición rechazan la
presencia de `is_active`, incluso si contiene un valor vacío. No se utiliza
`SoftDeletes`, no hay `deleted_at` y no se define ninguna acción HTTP de borrado.
Los campos ajenos al contrato nunca se asignan al modelo mediante la API.

Para la futura relación con cuentas institucionales, `institutions.id` será la
referencia estable. La clave foránea en usuarios y las relaciones Eloquent se
implementarán junto con HU-S1-03; esta entrega no modifica cuentas ni sus permisos.

## Contrato API

Todas las rutas aplican `auth:sanctum`, `active` y `role:ADMIN`, con las sesiones
y protección CSRF existentes de HU-S1-01.

| Método y ruta | Cuerpo | Resultado |
| --- | --- | --- |
| `GET /api/institutions` | — | `200`, `{data: [...]}` con activas e inactivas ordenadas por ID. |
| `POST /api/institutions` | `name`, `cct`, `contact_email` | `201`, `{data: {...}}` con el registro creado y activo. |
| `GET /api/institutions/{institution}` | — | `200`, `{data: {...}}`. |
| `PUT /api/institutions/{institution}` | Los tres campos obligatorios | `200`, `{data: {...}}` con los datos actualizados. |
| `PATCH /api/institutions/{institution}/status` | `is_active`: `true` o `false` | `200`, `{data: {...}}` con el estado solicitado. |

Los objetos incluyen `id`, `name`, `cct`, `contact_email`, `is_active`,
`created_at` y `updated_at`. El listado vacío devuelve `{data: []}`.
La acción de estado rechaza `name`, `cct` y `contact_email`, y repetir el mismo
estado conserva ese estado. Los datos solo se escriben después de validar la
solicitud completa. Si dos altas o ediciones compiten por un CCT, la restricción
UNIQUE es la última garantía y la API responde con error de validación del CCT.

Errores: `401` sin sesión válida o con cuenta desactivada; `403` por rol;
`404` por institución inexistente o identificador inválido/fuera de rango;
`419` por CSRF; `422` por datos inválidos.
`DELETE /api/institutions` y `DELETE /api/institutions/{institution}` responden
`405` porque no son métodos admitidos y no eliminan registros.

## Cobertura de aceptación

| Criterios | Cobertura en `backend/tests/Feature/InstitutionTest.php` |
| --- | --- |
| CA-01, CA-14 | Matriz de todos los endpoints: ADMIN permitido, visitantes rechazados y los otros tres roles rechazados sin modificaciones. |
| CA-02, CA-06 | Listado vacío y mixto; consulta individual e inexistente. |
| CA-03, CA-08, CA-09 | Alta válida, campos persistidos, estado booleano activo y default en DB. |
| CA-04, CA-13 | Obligatoriedad, tipos, límites y email; solicitudes inválidas sin altas ni modificaciones parciales. |
| CA-05 | Unicidad al crear y editar, CCT propio permitido, CCT inactivo reservado, restricción UNIQUE en PostgreSQL y colisión posterior a la validación simulada durante la escritura. |
| CA-07 | Edición válida y asignación exclusiva de campos autorizados. |
| CA-10, CA-11 | Inactivación y reactivación conservan ID, datos y registro consultable; estado inválido no modifica datos. |
| CA-12 | Ausencia de rutas DELETE y rechazo de intentos directos sin pérdida de información. |
| Integración HU-S1-01 | Sesiones y CSRF reales, administradores desactivados y regresión completa del backend. |

migraciones a la base de desarrollo; la nueva migración se aplica allí mediante
`docker compose exec backend php artisan migrate` cuando se prepare ese entorno.
